# 0006 Test design: feature by layer, priority as a tag

Context: the author's suites at Hublo were designed on a grid per feature: `@happy-path`, `@validation-error` (missing or null field, empty payload, negative, zero), `@error-case` (401, 403, 404 per resource), plus feature tags. Read per endpoint, the grid shows a documented status nobody tests as an empty cell. Laid on it, the first cut of this suite had 401 on 3 of 10 operations. The brief's Priority column was a cell of the docs that nothing but the report read, on two levels of three.

Decision: every `test()` carries its folder tag, exactly one layer tag and exactly one priority tag, `@p1`, `@p2`, `@p3`, equal to the Priority cell of its docs row; `npm run traceability` fails otherwise. `test-scenarios.md` opens with the grid: one row per operation, its documented statuses, the scenario IDs per layer; a status is in a cell or in "Left out" with a reason. Then the priority table: each level defined by what a failure costs for this service, with its scenarios. Three layers as at Hublo: 409 and 400 `INVALID_TRANSITION` are error cases, 422 `INCOMPLETE_OFFER` and a `reject` without reason are validation errors. A test that proves two things is two tests under one ID. The priority is a third axis, not a function of the layer: WFL-003 is a validation error and P1, WFL-006 a happy path and P2, VAL-003 a happy path and P3. A tier (`@smoke`, `@sanity`, `@regression`, `@release-check`) is a fourth tag in e2e-tests only: it says when a test runs, which matters for a browser suite on a shared demo and not for an API suite that runs in seconds against a stub.

Consequences: `--grep @error-case` runs a layer, `--grep @p1` the critical set; `npm run report:scenarios` reads the priority from the tags in `results.json` and fails on a P1 not passed, so a priority is written once in the docs and copied to the test, never a third time; a new operation is a row of the grid before it is a test; a boundary comes in pairs (`amount` -1 refused, 0 accepted).
